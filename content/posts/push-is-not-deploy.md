有一種失敗，它的每一步看起來都成功了。

AI 寫完 code。測試綠燈。commit 過了。push 上去，CI 顯示打勾。AI 在總結裡寫下「**已完成部署**」。

然後隔天客戶說：功能沒出現。

---

## 每一步都對，結果是錯的

回去查，你會發現真相通常是這幾種之一：

- CI 綠燈，但那個 workflow 監聽的是另一個分支
- 部署跑了，但 build 產物沒同步到正式目錄
- 檔案上去了，但 CDN 還在吐舊的
- 容器重啟了，但吃的是舊的 image
- 全都對了，只是那台 self-hosted runner 沒開機

**沒有任何一步「失敗」，所以沒有任何一步會拋錯。**

AI 看到的最後一個訊號是 `push` 回傳 0，於是它合理地推論「完成了」。這個推論在 90% 的情況下是對的——而剩下 10% 就是你在客戶面前丟臉的那些。

---

## 為什麼這件事在 AI 協作下變嚴重

人類工程師有一個不會寫進 SOP 的習慣：**push 完會順手開一下網頁。**

那個動作沒有名字、不在任何流程文件裡、也沒人教過。但它是真正的驗證。

AI 沒有這個習慣，因為它沒有「順手」這回事。它只做被要求做的事。你說「幫我部署」，它就 push；push 成功了，任務就完成了。它不會無聊到自己去開網頁看一眼——**除非你把「開網頁看一眼」寫成任務的一部分。**

這就是 agentic coding 的隱藏成本：**所有人類靠直覺補上的縫隙，都得被明文化，否則它們會全部裂開。**

---

## 別信版號，別信時間戳

最常見的錯誤驗證方式，是去看版號或建置時間。

```
"version": "1.4.2"   ← 這個數字在 build 的時候就寫死了
```

它證明的是「**這份 code 被建置過**」，不是「**這份 code 現在正在線上服務**」。

同樣的道理：

- **時間戳** —— 建置時間，不是部署時間
- **CI 綠燈** —— 建置成功，不是部署成功
- **`git log` 有那個 commit** —— 進了 repo，不是進了伺服器

這三個東西的共同點是：**它們都在部署發生之前就已經確定了。** 拿部署前的證據去證明部署後的狀態，邏輯上就不成立。

### 那要看什麼

看**只有新版本才會有的東西**：

```bash
# 打健康檢查，看回傳的 build id / commit hash
curl -s https://your.site/health

# grep 線上 bundle 有沒有這次才加的特徵字串
curl -s https://your.site/ | grep -c "這次新增的某個字串"

# 容器年齡——剛部署的應該是「幾分鐘前」
docker ps --format '{{.Names}}\t{{.Status}}'
```

原則很簡單：**去找一個「舊版本不可能通過」的檢查。**

我自己最常用的是最後一種：抓一段這次才寫進去的文字，去線上 grep。它不會騙人——那串字如果在，新 code 就真的在服務。

## 一個真實的例子

前陣子我要把三篇案例研究發到自己公司的官網上。

流程看起來很單純：改完、commit、push 到 `main`。CI 會自動部署。

推之前我多做了一步——**去看部署設定檔到底監聽哪個分支**。

```yaml
on:
  push:
    branches: [release]   # 不是 main
```

主線是 `release`，不是 `main`。而 `release` 比 `main` 領先了 28 個 commit，裡面包含**五篇已經上線的部落格文章**、`robots.txt`、還有一批 `web.config` 的編碼修正。

而部署腳本用的是：

```powershell
robocopy dist C:\inetpub\wwwroot\Site /E /PURGE
```

`/PURGE` 會刪掉目標目錄裡所有不在本次建置產物中的檔案。

**如果我照原計畫從 `main` 推出去，那五篇文章和 robots.txt 會從線上消失。** 而 CI 會顯示綠燈，因為部署本身完全成功了。

沒有任何一步會報錯。

## 所以我把收工寫成了規則

這件事讓我意識到：問題不在那一次差點出事，在於**我沒有一套「收工」的流程**。

開工的流程大家都有——讀 context、確認需求、開分支。但收工呢？多數人（包括 AI）的收工就是 push 完說一聲「好了」。

所以我把它明文化成四條線，做成一個 [Claude Code skill](https://github.com/youllook/wrap-up)。說一句「收工」就跑完：

**1. 壓縮記憶** —— 只掃這次 session 碰到的，不全量重讀。逐條判斷「留結論、砍過程」。
有一條規則特別容易做錯：*環境真相常常偽裝成踩坑故事*。「原來這個 API key 綁 IPv4 白名單」看起來像 debug 心得，其實是環境事實——要先把那句真相抽出來歸檔，**再**砍掉原文。

**2. 清理分支** —— 標籤不可信，查實況。`git rev-list --count origin/main..<branch>`，0 ahead 才是真的收斂。
還沒併的不擅刪，但列一張陳情表，逼一個「續做／併掉／棄單」的裁決。沒空裁就下次再列——**擱置天數持續上升，本身就是提醒。**

**3. 發布與驗證** —— 絕不 `git add .`；staged 內容過一次 secret 掃描；然後**確認部署真的落地**（就是這篇在講的事）。

**4. 寫明日第一步** —— 一行，寫進 `MEMORY.md` 頂部。
寫「動作」不寫「狀態」：「跑正式站轉單主線驗真 LLM」✓，「轉單系統待驗證」✗。
因為 `MEMORY.md` 每次都會自動載入，這行就是隔天的開場白。

## 真正的收穫不是那個 skill

是這個觀念：

> **「驗證」不是流程的最後一步，它是流程唯一有意義的一步。**

前面所有步驟——寫 code、測試、commit、push——都只是**製造一個可能性**。只有驗證能把可能性變成事實。

而在 AI 協作的情境下，這件事變得更重要，因為 AI 非常擅長讓每一步「看起來成功」。它會回報 `exit 0`，會說「已完成」，會在總結裡寫得條理分明。

**它不是在騙你。它只是把「沒有錯誤」當成了「成功」。**

這兩件事之間的差距，就是你還需要在場的理由。

---

## 一句話

`git push` 只證明你的 code 離開了本機。

**要證明它活著，你得去戳它一下。**
